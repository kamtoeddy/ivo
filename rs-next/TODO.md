# Open

- [ ] investigate potential performance (memory and speed) enhancements. Baseline context: `/rs-next` is already -40% to -99% vs `/rs` across every existing benchmark (`scripts/benches/RESULTS.md`), so this is refinement of an already-strong baseline, not a regression fix. Two independent sub-investigations:
  - [x] the original "static strs"/"arrays instead of Vec" sub-items were about the derive macro's *own* internal compile-time data structures (`crates/derive/src/lib.rs`'s `String`/`Vec` fields on its parsing/codegen types like `DependentInfo`, `VField`, `StructArgs`, `FieldDef`), not the generated runtime schema code -- checked each cited site specifically and closed with no actionable change: the `String` fields (`name_str`, etc.) already follow a compute-once-then-reuse-across-several-`quote!`-sites pattern, and there's no cheaper alternative (`Ident::to_string()`/`LitStr::value()` both allocate inherently, nothing to borrow instead). The `Vec<T>` fields (`derives`, `attrs`, `validate_items`, etc.) hold genuinely variable-length data straight from the `syn` AST -- correct type for that, arrays aren't an option (unknown length), and typical counts (single digits per field/schema) make even a stack-inline `SmallVec` an immeasurable win against everything else a `cargo build` does. No profiling needed to close this one; the reasoning is structural.
  - [ ] separate, real finding from an earlier `cargo expand` pass on the *generated* (runtime) `create`/`update` code: `IvoContext` (`src/internals/types.rs`) owns its `input`/`output` rather than borrowing it, and gets rebuilt via `input.clone()` + `output.clone()` after every phase transition -- confirmed 9 rebuilds in `create`, 9 in `update`, plus every resolver/lifecycle-hook trigger clones `ctx` again by taking it by value (likely structural: each concurrent handler in a `join!` batch needs an owned snapshot). Most plausible real runtime cost driver for schemas with several heap-allocated fields, but unmeasured -- reading generated code shows the pattern exists, not how much it costs. Recommend profiling (e.g. `cargo flamegraph` on the memory-stress benches) before attempting a fix, since making `IvoContext` borrow instead of own would be a real architecture change touching every handler signature and the `join!` concurrency model -- deserves its own scoped plan, not a casual change. Not yet decided whether to pursue -- ask before proceeding.
- [x] update docs (and README) of `rs-next` -- `README.md` done; the hosted docs site (`docs/docs-rs/*`, all 11 pages + French translations) rewritten for `v0.5.0`'s `#[ivo_schema]` API, and the interactive WASM playground (`docs/wasm/ivo-playground/`) rebuilt against `rs-next` too. See `docs/TODO.md` for the full breakdown.
- [x] found while rebuilding the docs' WASM playground against `rs-next` (`docs/wasm/ivo-playground/`, compiled for `wasm32-unknown-unknown`): `IvoRwCtxOptions`/`IvoCtxOptions`'s `read_sync()`/`write_sync()` didn't compile *at all* on `wasm32` -- `async-lock`'s `read_blocking()`/`write_blocking()` primitives they're built on are `#[cfg(not(target_family = "wasm"))]`-gated in that crate (no OS thread to block on that target), and the derive macro calls `read_sync()` internally for *any* fully-synchronous schema (to read `ctx_options` for the error-sanitizer call when `create`/`update` can't `.await`), so this broke compiling `ivo` itself for wasm32, not just schemas that happen to call these methods directly. Fixed by keeping the real OS-thread-blocking implementation on native (`#[cfg(not(target_family = "wasm"))]`, preserves the already-tested concurrency guarantees in `tests/extras/ctx_options/sync_concurrency.rs` unchanged) and adding a `#[cfg(target_family = "wasm")]` counterpart that uses `try_read()`/`try_write()` (non-blocking, no target gate, panics if actually contended) instead -- safe because of the same "never actually contended within ivo's own pipeline" reasoning already documented on these methods. Verified: `cargo test --workspace` (843+46, unchanged, confirms native behavior/tests untouched) and a real `wasm-pack build` + Playwright e2e test actually executing the compiled demos in a browser (both passing).
