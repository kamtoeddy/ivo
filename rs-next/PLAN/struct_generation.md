# Plan: Input/output struct generation

## Goal

The `#[ivo_schema]` macro generates the input and output structs from the schema definition, instead of requiring users to define and keep them in sync manually. The existing `#[derive(IvoInputStruct)]` and `#[derive(IvoStruct)]` macros are still used, but they are applied automatically to the generated structs.

## Generated items

For a schema with input-only or output-only fields, both structs are declared:

```rust
#[ivo_schema(input = UserInput, output = User)]
mod user_schema { ... }
```

The macro emits:

```rust
#[derive(Clone, Debug, Default, PartialEq, IvoInputStruct)]
pub struct UserInput { ... }

#[derive(Clone, Debug, Default, PartialEq, IvoStruct)]
pub struct User { ... }

// Generated by the derive macros:
// pub struct PartialUserInput { ... }
// pub struct PartialUser { ... }
// pub struct UserInputErrors<Metadata> { ... }

pub struct UserSchemaModel { ... }
```

For a schema with only `#[required]` and/or `#[lax]` fields and no `#[timestamps]`, a single struct is sufficient:

```rust
#[ivo_schema(input = User)]
mod user_schema { ... }
```

The macro emits one struct and derives both traits:

```rust
#[derive(Clone, Debug, Default, PartialEq, IvoInputStruct, IvoStruct)]
pub struct User { ... }

// Generated by the derive macros:
// pub struct PartialUser { ... }
// pub struct UserErrors<Metadata> { ... }

pub struct UserSchemaModel { ... }
```

## Field placement rules

| Field type                | Input struct | Output struct               | Notes                                                                           |
| ------------------------- | ------------ | --------------------------- | ------------------------------------------------------------------------------- |
| `#[required]`             | field name   | field name                  | Neither input-only nor output-only                                              |
| `#[lax]`                  | field name   | field name                  | Neither input-only nor output-only                                              |
| `#[constant]`             | —            | field name                  | Output-only                                                                     |
| `#[dependent]`            | —            | field name                  | Output-only                                                                     |
| `#[virtual]` (no alias)   | field name   | —                           | Input-only; must be referenced by at least one dependent field                  |
| `#[virtual(alias = "X")]` | alias `X`    | —                           | Input-only; alias must name a dependent field that depends on the virtual field |
| `#[created_at]`           | —            | field name                  | Output-only; type is the timestamp type returned by the resolver                |
| `#[updated_at]`           | —            | field name or `Option<...>` | Output-only; `Option<T>` is treated as optional                                 |

A schema has no input-only or output-only fields when it contains only `#[required]` and/or `#[lax]` fields and no timestamp fields. In that case the input struct is reused as the output struct.

## Visibility

The generated items inherit visibility from the schema module and from individual field declarations.

- **Input/output structs** use the visibility of the `#[ivo_schema]` module.
  - `pub mod user_schema { ... }` → `pub struct UserInput { ... }` / `pub struct User { ... }`.
  - `mod user_schema { ... }` → structs with no visibility keyword.
- **Fields** default to `pub`. An explicit Rust visibility keyword on the field declaration is preserved:
  - `name: String` → `pub name: String`.
  - `pub(crate) internal_id: Uuid` → `pub(crate) internal_id: Uuid`.
  - `#[visibility(private)]` forces the field to be emitted with no visibility keyword, even in a `pub` struct.
- **Timestamp fields** are declared as normal fields with `#[created_at]` / `#[updated_at]`, so they follow the same visibility rules as any other field. The shared resolver is declared separately in `#[options]` via `#[timestamps(...)]` and does not carry visibility.
- **Partial structs and error structs** use the same visibility as their corresponding input/output struct.
- **The generated schema model** (`UserSchemaModel`) uses the same visibility as the output struct.

## Detailed rules

### Required and lax fields

These are the simplest: the field name is added to both `UserInput` and `User` with the declared type.

```rust
#[required]
name: String,

#[lax("user")]
role: String,
```

generates:

```rust
pub struct UserInput {
    pub name: String,
    pub role: String,
}

pub struct User {
    pub name: String,
    pub role: String,
}
```

### Constant fields

Constant fields are output-only. The field name is added only to `User`.

```rust
#[constant(|| Uuid::new_v4())]
id: Uuid,
```

generates:

```rust
pub struct User {
    // ... other fields
    pub id: Uuid,
}
```

The input struct must not contain a field named `id`; the macro emits a compile error if it would.

### Dependent fields

Dependent fields are output-only. The field name is added only to `User`.

```rust
#[dependent(on = [age])]
#[resolve(|ctx, _opts| async move { format!("{}", ctx.values().age.unwrap_or(0)) })]
age_label: String,
```

generates:

```rust
pub struct User {
    // ... other fields
    pub age: i32,
    pub age_label: String,
}
```

The parent fields (`age` in this example) must exist in the schema and are added to both structs according to their own field type.

### Virtual fields without alias

Virtual fields are input-only. The field name is added to `UserInput` and consumed by dependent fields; it is not added to `User`.

```rust
#[virtual]
#[sanitize(|email, _ctx, _opts| async move { email.to_lowercase() })]
email: String,

#[dependent(on = [email])]
#[resolve(|ctx, _opts| async move { ctx.input().email.clone().unwrap() })]
raw_email: String,
```

generates:

```rust
pub struct UserInput {
    // ... other fields
    pub email: String,
}

pub struct User {
    // ... other fields
    pub raw_email: String, // dependent field that consumed the sanitized virtual
}
```

A virtual field without an alias must be referenced by at least one dependent field's `on = [...]`. Otherwise the macro emits a compile error.

### Virtual fields with alias

When a virtual field has an alias, the alias is the input field. The alias must name a dependent field in the schema, and that dependent field must depend on the virtual field. The virtual field name itself is not added to either struct; it is only an intermediate sanitized value.

```rust
#[virtual(alias = "raw_email")]
#[sanitize(|email, _ctx, _opts| async move { email.to_lowercase() })]
email: String,

#[dependent(on = [email])]
#[resolve(|ctx, _opts| async move { ctx.input().email.clone().unwrap() })]
raw_email: String,
```

generates:

```rust
pub struct UserInput {
    // ... other fields
    pub raw_email: String, // alias, not "email"
}

pub struct User {
    // ... other fields
    pub raw_email: String, // dependent field that consumed the sanitized virtual "email"
}
```

Rules:

- The alias (`raw_email`) must differ from the virtual field name (`email`).
- The alias must be the name of a dependent field.
- That dependent field must list the virtual field in its `on = [...]`.
- The alias is added to `UserInput`; the virtual field name is not added to either struct (it is only an intermediate sanitized value consumed by the dependent field).

### Timestamps

Timestamp fields are declared in `#[fields]` with `#[created_at]` or `#[updated_at]`. They are added to `User` only. Their names, types, and visibilities come directly from the field declarations.

```rust
#[fields]
mod fields {
    #[created_at]
    pub created_at: DateTime<Utc>,

    #[updated_at]
    pub updated_at: DateTime<Utc>,
}

#[options]
mod options {
    #[timestamps(|| Utc::now())]
    const _: () = ();
}
```

generates:

```rust
pub struct User {
    // ... other fields
    pub created_at: DateTime<Utc>,
    pub updated_at: DateTime<Utc>,
}
```

Rules:

- At most one `#[created_at]` field and at most one `#[updated_at]` field may be declared.
- Timestamp field names cannot be reused as schema field names or virtual aliases.
- An `#[updated_at]` field typed as `Option<T>` is treated as optional (set only if already present); `T` is always set.
- Optional detection is syntactic (`Option<T>`) and does not resolve type aliases.

## Validation performed by the macro

The macro performs the same checks that the current runtime `make_field_configs` does, but at compile time:

1. **Duplicate field names** — no two schema fields can share a name.
2. **Single-struct eligibility** — if the schema contains only `#[required]`/`#[lax]` fields and no timestamp fields, only `input = ...` is allowed. If it contains any `#[virtual]`, `#[constant]`, `#[dependent]`, `#[created_at]`, or `#[updated_at]`, both `input = ...` and `output = ...` are required.
3. **Constants on output only** — constant field names must not appear on the generated input struct.
4. **Dependents on output only** — dependent field names must not appear on the generated input struct.
5. **Virtual alias validity** — alias must name a dependent field that depends on the virtual field.
6. **Virtual without alias must have dependents** — a virtual field without an alias must be a dependency of at least one dependent field.
7. **Virtual field name placement** — virtual field names are not added to the output struct; only their aliases (if any) appear on input, and the dependent fields they feed appear on output.
8. **Timestamp field limits** — at most one `#[created_at]` field and at most one `#[updated_at]` field may be declared. Timestamp field names cannot clash with schema field names or aliases.
9. **Timestamp resolver** — if any timestamp field is declared, exactly one `#[timestamps]` resolver must be declared in `#[options]`.
10. **Parent field existence** — every field referenced in `#[dependent(on = [...])]` must exist in the schema.
11. **No self-dependency** — a dependent field cannot depend on itself.
12. **No timestamp dependencies** — dependent fields cannot depend on timestamp fields.
13. **Field visibility** — field declarations may include a standard Rust visibility keyword (`pub`, `pub(crate)`, `pub(super)`, etc.) or `#[visibility(private)]`, but not both. The macro emits `compile_error!` for invalid visibility syntax.

## Interaction with derive macros

In dual-struct mode, the generated structs are annotated with:

```rust
#[derive(IvoInputStruct)]
pub struct UserInput { ... }

#[derive(IvoStruct)]
pub struct User { ... }
```

In single-struct mode, the single struct derives both traits:

```rust
#[derive(IvoInputStruct, IvoStruct)]
pub struct User { ... }
```

These derives generate:

- `PartialUserInput` and `PartialUser` (or just `PartialUser` in single-struct mode)
- `UserInputErrors<Metadata>` (or `UserErrors<Metadata>` in single-struct mode)
- The internal methods consumed by `UserSchemaModel`

Users do not write these derives by hand.

## Open questions

1. Should the macro support referencing existing structs instead of generating them? This could be useful for adding custom methods or impls, but complicates the macro.
2. Should struct visibility be inherited from the schema module, or configurable via an attribute?
3. How should doc comments on schema fields propagate to the generated struct fields?

## Implementation plan

1. Add struct generation to the `#[ivo_schema]` macro expansion.
2. Detect single-struct vs dual-struct mode from the schema contents and the `input`/`output` arguments.
3. Implement field placement logic based on field type and alias.
4. Emit compile-time errors for invalid placements or missing struct arguments.
5. Apply `#[derive(IvoInputStruct)]` and `#[derive(IvoStruct)]` to the generated structs (or both derives on a single struct in single-struct mode).
6. Ensure generated partial/error structs are visible and used by `UserSchemaModel`.
7. Port existing `rs` tests to use generated structs.
